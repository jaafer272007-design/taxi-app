# بريف تقني — Phase 1 (MVP)
**النموذج:** السائق يعلن مسار + الراكب يحجز مقعد · ممر **النجف↔كربلاء** · مشترك بالمقعد · door-to-door · cash · Android.
**الغرض:** وثيقة بناء لـ Claude Code — module-by-module.

---

## 0. النطاق
**داخل Phase 1:** WhatsApp OTP · اعتماد سائق + مستمسكات · السائق يعلن رحلة (مجدولة أو "الآن") · بحث الراكب + حجز مقعد (door-to-door) · دورة حياة الرحلة · تحصيل نقدي + أرباح · تقييم متبادل · إشعارات · لوحة أدمن أساسية.
**خارج Phase 1 (لا تبنيه):** ❌ تجميع النظام (system-pooling) ❌ الطلب الآني بالمطابقة الحية ❌ دفع رقمي/محفظة ❌ iOS ❌ ممرات متعددة ❌ surge/كوبونات ❌ تتبّع لحظي كامل للموقع (يكفي حالة الرحلة + معلومات السائق).

---

## 1. الـ Stack المعتمد
- **API:** NestJS (modular monolith) · **ORM:** Prisma (قابل للتبديل لـ TypeORM) · **DB:** PostgreSQL (+ PostGIS متاح، بس Phase 1 يستعمل lat/lng بسيط) · **Cache:** Redis.
- **Mobile:** Flutter (كود واحد، شاشات راكب/سائق) — Android.
- **Admin:** React/Next.js.
- **Auth:** JWT + WhatsApp Business Cloud API للـ OTP (أعِد استخدام إعداد Sehat Beitak).
- **Push:** FCM.
- ثوابت: عملة **IQD**، توقيت **Asia/Baghdad**، لغة **عربي RTL**، هاتف **+964**.
> تبديل أي عنصر بالـ stack ما يغيّر تصميم الـ modules/endpoints أدناه.

//
// **ليش جدول، و`BookingStatus.NO_SHOW` موجود أصلاً؟** الحالة تجيب على سؤال
// واحد: كيف انتهى هذا الحجز. والسياسة تسأل ثلاثة أسئلة أخرى لا يجيب عنها:
//   ١) **متى** وقعت — النافذة المتدحرجة تحتاج طابعاً زمنياً للواقعة نفسها،
//      و`SeatBooking` ما عنده إلا `createdAt` (لحظة الحجز، لا لحظة الغياب)
//      و`departureTime` على الرحلة. عدّ الحالات كان سيعدّ حجوزات قديمة
//      أُشّرت اليوم كأنها وقعت اليوم، والعكس.
//   ٢) هل **أُلغيت** — التظلّم يحتاج «واقعة مُلغاة» تبقى مرئية بلا أن تُحتسب.
//      لا يمكن تمثيلها بإرجاع الحجز إلى `COMPLETED` (كذب: الراكب ما ركب)
//      ولا إلى `CANCELLED` (كذب آخر: الراكب ما ألغى، والمقعد ما رجع للبيع).
//   ٣) **مَن** ألغى و**لماذا** — سجل التظلّم، وهو الإشارة الوحيدة التي
//      ستخبرنا لاحقاً أن العتبة خاطئة.
// الحالة تبقى مصدر الحقيقة لـ«حال هذا الحجز»؛ هذا الجدول مصدر الحقيقة
// لـ«سجل هذا الراكب». يُكتبان معاً في **معاملة واحدة**.

  riderId   String
  tripId    String

  createdAt DateTime @default(now())

  // الدليل على أن أحداً راجع الحالة أصلاً.
  voidedAt   DateTime?
  voidedBy   String?              // AdminUser.id
  voidReason String?              // مطلوب عند الإلغاء (≥ ٣ أحرف)

  // ترتيب الفهرس = ترتيب الشرط في كل استعلام عدّ.
  @@index([riderId, voidedAt, createdAt])
}

//
// ٣٠٦ ممرات والسائقون يعلنون على حفنة منها؛ الراكب الذي يبحث في مسار فارغ
// يرى حالة صحيحة ثم يغادر ولا نتعلّم شيئاً. هذا الصف هو ما يحوّل ذلك المأزق
// إلى معلومة.

// **ليس `SeatRequest`.** ذاك (Phase 2) طلب مقعد آنيّ يدخل مطابقة حية مع سائق؛

model RouteRequest {
  id         String   @id @default(cuid())
  riderId    String                        // User.id، بلا relation مثل SeatBooking
  corridorId String
  corridor   Corridor @relation(fields: [corridorId], references: [id])

  requestedFor DateTime?                   // التاريخ الذي كان يبحث عنه، إن حدّده

  // يوم بغداد كـ DATE. موجود **حصراً** ليحمل الفهرس الفريد أدناه: قاعدة
  // «طلب واحد لكل راكب لكل ممر في اليوم» قيدُ قاعدة بيانات لا حارس تطبيق —
  // نقرتان متزامنتان على شبكة بطيئة تمرّان من أي حارس، والعدّ هو كل القيمة.

  fulfilledByTripId String?

  @@unique([riderId, corridorId, requestedDay])
  @@index([corridorId, fulfilledAt, createdAt])
}

## 3. آلات الحالة
**Trip:** `OPEN` (يقبل حجوزات) → `LOCKED` (امتلأ أو حان الوقت) → `EN_ROUTE` (السائق بدأ) → `COMPLETED` → `SETTLED`. أي وقت قبل EN_ROUTE → `CANCELLED`.
**SeatBooking:** `CONFIRMED` → `ONBOARD` (اختياري) → `COMPLETED`. أو `CANCELLED` (قبل القطع) / `NO_SHOW` (السائق يأشّرها).
> **Phase 1 amendment — القطع صار حالةً لا ساعة:** `CANCELLED` بيد الراكب مسموح
> ما دامت **الرحلة** `OPEN`/`LOCKED`، ومرفوض من `EN_ROUTE`. و`NO_SHOW` **لا
> تُقبل قبل `EN_ROUTE`** — فلا تتقاطع الحالتان أبداً: قبل الانطلاق الإلغاء
> فقط، وبعده الغياب فقط. راجع `no-show`.

## 4. الـ Modules + الـ Endpoints

### `auth`
- `POST /auth/request-otp` `{ phone }` → يرسل OTP عبر واتساب.
- `POST /auth/verify-otp` `{ phone, code }` → JWT (يُنشئ User إذا جديد).
- `GET /auth/me` → يرجّع `{ …, gender, profileComplete }`.
- `PATCH /auth/me` `{ name?, gender?, emergencyContact? }` → تحديث جزئي (كل حقل اختياري ويُكتب وحده). **Phase 1 amendment:** `emergencyContact` كائن **يضبط**، `null` **يمسح**، وغيابه **لا يغيّر** — راجع `safety`. **Phase 1 amendment:** `gender` (`MALE|FEMALE`) مطلوب لإكمال الملف؛ الملف **مكتمل** فقط عند ضبط الاسم **و** الجنس معاً (`profileComplete`). المستخدمون القدامى `gender=null` = غير مكتمل حتى يضبطوه. جنس غير صالح → 400.
**قبول:** رقم عراقي يستلم كود واتساب ويدخل بنجاح؛ إعادة الإرسال محدودة (rate-limit)؛ ضبط الاسم والجنس يُكمل الملف.

### `admin-auth` (Phase 1 amendment — Step 7)
الأدمن يدخل بـ**اسم مستخدم + كلمة مرور**، مو WhatsApp OTP: المجموعة داخلية

#### تسعير الشبكة الأولي — من أين جاءت الأرقام

> **هذه تقديرات، مو بيانات مسح.** موجودة حتى يصير كل زوج مدن قابلاً للحجز من اليوم الأول برقم **معقول**، لا برقم **موثّق**. الأدمن يضبط كل ممر من اللوحة، والـ seed **لا يكتب فوق أي سعر معدّل**.

**المسافات.** بدل جدول مسافات يدوي بـ153 خانة، نخزن **إحداثيات تقريبية لمركز كل محافظة** (18 صفاً فقط) ونحسب المسافة بـ haversine — أقل عرضة للخطأ المطبعي، والنتيجة متماثلة تلقائياً، والإحداثية الغلط تنكشف على الخريطة بعكس خانة غلط بجدول. المصدر: `services/api/src/corridor/corridor-grid.ts`.

**معامل التواء الطريق = 1.10** (طريق فعلي ÷ خط مستقيم). **مُعايَر، مو مفترض:** قِيس مقابل تسع مسافات طرق معروفة (نجف–كربلاء ٨٠كم، بغداد–كربلاء ١٠٥، بغداد–نجف ١٦٠، بغداد–حلة ١٠٠، بغداد–بصرة ٥٥٠، بغداد–موصل ٤٠٠، بغداد–أربيل ٣٥٠، بغداد–كركوك ٢٤٠، أربيل–دهوك ١٥٠) فأعطى خطأ متوسط ~٦٪ مقابل ~٩٪ عند 1.20 و~١١٪ عند 1.25. منخفض لأن طرق العراق بين المحافظات صحراوية مستقيمة غالباً — وبالمقابل **يقلّل تقدير** الطرق الجبلية شمالاً، والأدمن يضبط الشواذ.

**الصيغة (شريحتان):**
```
السعر = 3,000  +  110 × (أول 100 كم)  +  55 × (ما بعد 100 كم)     ثم يُقرّب لأقرب 500 IQD
        └ أجرة أساس: الالتقاط، الانتظار، انحراف door-to-door بالطرفين
```
شريحتان لأن سعراً ثابتاً للكيلومتر ما ينفع لطرفَي البلد: الرحلة القصيرة تحكمها الكلفة الثابتة، والكيلومتر الإضافي بمشوار ٥٠٠كم أرخص بكثير. بسعر واحد للكيلومتر، تثبيت القصيرة يخلّي بغداد→البصرة تقريباً **ضعف** سعر المقعد الحقيقي.

**التثبيت:** المعامل 110 مختار حتى ينزل **النجف→كربلاء على ١٢٬٠٠٠ بالضبط** — السعر المستعمل فعلاً — وكل الباقي يتدرّج منه:

| المسار | طريق تقريبي | السعر المقترح |
|---|---|---|
| كربلاء→الحلة | ~٤٥ كم | ٨٬٠٠٠ |
| **النجف→كربلاء** | **~٨٢ كم** | **١٢٬٠٠٠** (مثبّت) |
| بغداد→النجف | ~١٦١ كم | ١٧٬٥٠٠ |
| بغداد→أربيل | ~٣٥٤ كم | ٢٨٬٠٠٠ |
| بغداد→البصرة | ~٤٩٣ كم | ٣٥٬٥٠٠ |
| البصرة→دهوك | ~٩١٨ كم | ٥٩٬٠٠٠ |

**الحدود:** `min = 60%` و `max = 160%` من المقترح، مقرّبة لأقرب ٥٠٠، ثم **مقصوصة** (`LEAST`/`GREATEST`) حتى يبقى `0 < min <= suggested <= max` بكل صف — نفس انضباط ترحيل «تسعير يحدده السائق»؛ التقريب لوحده يقدر يرفع `min` فوق المقترح بالأرقام الصغيرة، وممر بهذا الكسر يملأ للسائق سعراً يرفضه `POST /trips` فوراً.

**الحماية من الكتابة فوق التعديلات:** الـ seed يستعمل `createMany({ skipDuplicates: true })` — ما عنده مسار تحديث أصلاً، فما **يقدر** يمسح سعراً ضبطه الأدمن ولا يعيد تفعيل ممر عطّله عمداً. `upsert` بـ`update: {}` كان يتصرف نفس الشيء اليوم، بس يبعد تعديلاً واحداً طائشاً عن تصفير أسعار البلد كله بأول deploy.

**قواعد:** `seatsTotal ≤ vehicle.seats`. سائق مُعتمد فقط. `departNow=true` → departureTime=now، ونافذة صلاحية افتراضية 30 دقيقة (قابلة للتمديد) — التفاصيل بالقسم أدناه. **سائق أي جنس يقدر يعلن رحلة `WOMEN_FAMILY`** (تقييد الركّاب يُفرض عند الحجز، لا عند النشر).

#### متى تبقى الرحلة قابلة للالتقاط (نافذة «الآن») — قاعدة موحّدة

> **خلفية العطل:** `POST /trips` كان يخزّن رحلة «الآن» بـ`departureTime = now` ويوثّق نافذة ٣٠ دقيقة، بينما `GET /trips/search` يفلتر `departureTime > now`. كل طبقة صحيحة لوحدها، والنتيجة أن **كل رحلة «الآن» تختفي من بحث الركّاب خلال ثانية من نشرها**. العطل بالتفاعل بين الطبقتين، ولهذا ما التقطه أي اختبار وحدة.

القاعدة الآن **معرّفة مرة واحدة** بـ`services/api/src/trip/trip-window.ts`، ويستعملها البحث والحجز ومهمة الإنهاء:

| نوع الرحلة | تبقى قابلة للالتقاط حتى |
|---|---|
| **مجدولة** (`departNow=false`) | `departureTime` — أي تختفي فور فوات وقتها، بلا أي تسامح |
| **الآن** (`departNow=true`) | `departureTime + 30 دقيقة` (`DEPART_NOW_WINDOW_MINUTES`) |

- **ما وُسّع الفلتر للجميع عمداً:** فترة سماح شاملة كانت ستُرجع رحلات مجدولة فات موعدها فعلاً. الفلتر `OR` على النوعين، لا `gt` واحد مُرخى.
- **البحث والحجز يستعملان نفس الدالة** (`isCatchable` / `catchableTripFilter`). لو اختلفا يصير العطل أسوأ: الرحلة تظهر بالنتائج وعند الضغط على «احجز مقعد» يرد «انتهى وقت هذه الرحلة».
- **`GET /trips/mine` يرجّع `catchableUntil`** (محسوبة بالخادم) حتى يعرض تطبيق السائق «متاحة للحجز حتى الساعة …». التطبيق **لا** يحسب النافذة بنفسه — نسخة ثانية من القاعدة هي أصل المشكلة.

**الإنهاء (`TripExpiryJob`) — كان TODO، صار منفَّذاً:** مهمة مجدولة كل دقيقة (`@nestjs/schedule`) تتعامل مع كل رحلة `OPEN` فاتت نافذتها:

- **عليها ركّاب** → `LOCKED` (حان الوقت؛ السائق يكمل بمن معه — نفس انتقال §3).
- **بلا ركّاب** → `CANCELLED`. `LOCKED` كانت ستظهر «مكتملة الحجز» على رحلة ما ركبها أحد، وهذا عكس ما حصل.

> ظهور الرحلة للراكب **لا يعتمد** على هذه المهمة: الرحلة المنتهية مستبعَدة أصلاً بفلتر البحث ومرفوضة بحارس الحجز. المهمة للتنظيف (قائمة السائق وعدّادات لوحة الأدمن)، فلو تعطّلت ما تظهر رحلة شبح قابلة للحجز.

**الاختبارات:** `trip-window.spec.ts` (القاعدة + تطابق الدالة مع فلتر Prisma)، `trip-expiry.spec.ts` (الانتقالات)، و**`booking/trip-search.int-spec.ts`: نشر ثم بحث بالتسلسل مقابل قاعدة بيانات حقيقية** — تُشغَّل بـ`npm run test:int`. باقي الاختبارات تُموّه Prisma، و`findMany` مموّهة ما تطبّق `where` أصلاً، فما كانت لتلتقط العطل أبداً.
**قبول:** سائق مُعتمد يعلن رحلة نجف→كربلاء بمقاعد؛ تظهر OPEN.

### `trip-contacts` (تواصل السائق ↔ الراكب) — Phase 1 amendment

> **خلفية:** الاختبار الحي أظهر أن السائق يشوف تسمية نقطة الصعود
> («قرية الغدير السكنية») لكن ما يقدر يوصل الباب: ولا خريطة، ولا وسيلة اتصال.
> بالكراج العراقي الحقيقي **السائق دائماً يتصل** حتى يحدد المكان بالضبط.

- `GET /trips/:id/contacts` → `{ role: 'DRIVER'|'RIDER', contacts: [{ userId, name, phone, bookingId }] }`.

| المتصل | يستلم |
|---|---|
| **سائق الرحلة نفسه** | كل راكب عليه حجز غير ملغى |
| **راكب عليه حجز غير ملغى** | السائق، مرة واحدة |
| **أي أحد غيرهم** (وضمنهم راكب حجزه **ملغى**) | **403** |

**القرار المقفول: أرقام حقيقية، تُكشف فقط بعد وجود حجز.**
- **ليش أرقام حقيقية:** هيك يشتغل نظام الكراج الموجود أصلاً — الأرقام تُتبادل
  بلا وسيط. **واتساب** إلزامي مثل الاتصال: يشتغل على الواي-فاي، ينفع ورصيدك
  صفر، ويحمل موقعاً مدبّساً أو صورة الباب — وهذا ما تقدر عليه المكالمة.
- **ليش بعد الحجز فقط:** بلا هذا القيد يقدر أي شخص يجمع رقم كل سائق بمجرد
  التمرير على نتائج البحث. الحجز هو العلاقة، وبدونه ما في سبب للتواصل.
- **ليش الحجز الملغى يفقد الرقم:** المقعد رجع والأجرة سقطت، فما بقي بينهما شي.
  بالمقابل `NO_SHOW` و`COMPLETED` **يحتفظان** بالرقم — الرحلة صارت (أو كان
  مفروض تصير)، والحقيبة المنسية مكالمة حقيقية.
- **المكالمة المقنّعة (masked calling)** عبر مزوّد اتصالات هي الترقية المستقبلية
  لو ظهر سوء استخدام؛ تحتاج مزوّداً مدفوعاً غير متوفر الآن. القرار الحالي
  مقصود وقابل للمراجعة، مو إغفال.

**التنفيذ — نقطة واحدة:** `TripContactService` هو **المكان الوحيد بالخادم الذي
يغادره رقم هاتف**. لا البحث ولا `/trips/mine` ولا `/bookings/mine` يرجّع رقماً.
قاعدة صلاحية منسوخة بمكانين هي نفس نمط العطل الذي أخفى رحلات «الآن» — إلا أن
ذاك كلّف ظهوراً، وهذا يكلّف رقم كل سائق.

**الاختبارات:** `trip-contact.int-spec.ts` **مقابل قاعدة بيانات حقيقية**، لأن
القاعدة كلها داخل `where` في Prisma و**`findFirst` المموّهة ما تطبّق `where`
أصلاً** — فاختبار وحدة لحالة «الحجز الملغى مرفوض» يفحص الموك لا القاعدة. يغطّي:
راكب مؤكد، سائق، راكب **ملغى** (403)، مستخدم غريب (403)، راكب له حجز على رحلة
**أخرى** (403)، `NO_SHOW` (يُقبل)، وأن **البحث لا يحمل أي رقم**.

**الإحداثيات:** `GET /trips/:id/bookings` و`GET /bookings/mine` يرجّعان
`pickupLat/Lng` و`dropoffLat/Lng` مع التسميات — التسمية تقول الحي، والنقطة
وحدها تنفتح على خريطة وتُسلَّم لتطبيق ملاحة.

**الأرقام بالواجهة (استثناء موثّق من قاعدة الأرقام العربية-الهندية):** رقم
الهاتف يُعرض بأرقام **غربية** داخل `Directionality(ltr)` — لأنه **معرّف يُطلب
ويُطابَق مع دليل الهاتف**، لا كمية تُقرأ؛ و`+٩٦٤ ٧٧١…` بسطر RTL مع علامة `+`
هي نفس فخّ الـbidi الذي خلّى «٤ مقاعد» تُقرأ «٤٠ مقاعد». الإحداثيات كذلك:
تنسيق آلي، غربي وLTR.

**قبول:** السائق يضغط نقطة الصعود → يشوفها على خريطة → يفتح الملاحة؛ الراكب يشوف
نقطتيه ورقم السائق بعد الحجز، والاتصال وواتساب يشتغلان؛ ولا رقم يظهر بأي شاشة
قبل الحجز.

### `rating`
- `POST /ratings` `{ tripId, toUserId, score, comment }` (بعد COMPLETED فقط) · تحديث `ratingAvg`.
**قبول:** الطرفان يقيّمون بعضهم بعد اكتمال الرحلة.

#### تقييم الراكب للسائق — Phase 1 amendment

الخادم كان يدعم الاتجاهين من البداية (`assertSharedTrip` تشتغل بالاتجاهين،
و`recomputeAvg` تحدّث `DriverProfile.ratingAvg`)، لكن **تطبيق الراكب ما كان
عنده أي مسار للتقييم**: السائق يقيّم الراكب، والراكب ما عنده وين يقيّم.
النتيجة أن `ratingAvg` — وهو **بالضبط** ما يعتمد عليه الراكب باختيار الرحلة —
ما كان يمتلئ أبداً. إشارة ثقة ميتة أسوأ من غيابها، لأن النجوم الفارغة تُقرأ
كحُكم لا كنقص بيانات.

`GET /bookings/mine` صار يحمل:

| حقل | لماذا |
|---|---|
| `driverUserId` | مَن يُوجَّه له التقييم (`Trip.driverId` هو معرّف DriverProfile لا User) |
| `driverName` | اسم يظهر بورقة التقييم |
| `ratable` | الرحلة صارت فعلاً — يُحسب بالخادم ليطابق ما يقبله `POST /ratings` |
| `ratedDriver` | هذا الراكب قيّم هذا السائق لهذه الرحلة مسبقاً |

> **لا رقم هاتف هنا.** الرقم يبقى خلف `GET /trips/:id/contacts` وحده.

`ratable` محسوب بالخادم عمداً: **إجراء تعرضه الواجهة ويرفضه الخادم أسوأ من
غياب الإجراء**، فالاثنان يشتقّان من نفس الحالات (`isRatableByRider`).
و`409` من `POST /ratings` يُعامَل **نجاحاً** بالطرفين — التقييم موجود أصلاً،
وهذه هي الحالة التي أرادها المتصل.

**قبول:** بعد اكتمال الرحلة يرى الراكب «قيّم السائق» على الحجز بـ«سابقة»
وتذكيراً أعلى «حجوزاتي»؛ التقييم يرفع `ratingAvg` فعلياً؛ ولا يمكن التقييم
مرتين ولا قبل الاكتمال.

### `no-show` (عواقب عدم الحضور) — Phase 1 amendment

**المشكلة:** الراكب الذي يحجز ولا يحضر يكلّف السائق **مقعداً كاملاً بلا أجرة** —
على سيارة بأربعة مقاعد هذه **٢٥٪ من دخل الرحلة** — ولا شيء يمنع التكرار.
السائقون هم القيد الأصعب بهذا السوق، وتطبيق يكلّفهم مالاً بلا حماية يخسرهم.

**القرار المقفول: سمعة + إيقاف مؤقت متصاعد، لا رسوم.** الدفع نقدي بالكامل بالـ
Phase 1، فما في وسيلة دفع مخزّنة نخصم منها؛ أي «رسم عدم حضور» يبقى رقماً بلا
تحصيل — عقوبة على الورق. الشيء الوحيد الذي نملكه فعلاً هو **الوصول للمنصّة**.

#### الأرقام (قابلة للضبط من البيئة)

| المتغيّر | الافتراضي | المعنى |
|---|---|---|
| `NO_SHOW_BLOCK_THRESHOLD` | **٣** | وقائع غير ملغاة توجب الإيقاف |
| `NO_SHOW_WINDOW_DAYS` | **٣٠** | طول النافذة المتدحرجة |
| `NO_SHOW_BLOCK_DAYS` | **٧** | مدة الإيقاف، **من آخر واقعة** |

**٣ وليس ٢:** مرة حادث، ومرتان قد تكونان سوء حظ (ازدحام، طارئ عائلي)؛ ٣ خلال
شهر نمط. **٧ أيام** تُشعَر ولا تطرد — الهدف تغيير سلوك لا خسارة راكب.
هذه **أرقام سياسة لا ثوابت هندسية**، وأول شهر تشغيل حقيقي سيغيّرها — لذلك هي
بيئة لا كود. القيمة الفاسدة ترجع للافتراضي بدل أن تُسقط الإقلاع.
القاعدة نفسها بلا قاعدة بيانات ولا Nest: `booking/no-show-policy.ts`.

**الإيقاف يبدأ من آخر واقعة، لا من لحظة العدّ** — وإلا لتجدّد نفسه كلما فتح
الراكب التطبيق فما ينتهي أبداً ما دامت الوقائع داخل النافذة.

#### ماذا يفعل الإيقاف وماذا لا يفعل

- **يمنع الحجوزات الجديدة فقط.** الفحص يجري بـ`BookingService.book()` **قبل**
  معاملة المقعد (نفس موضع فحص أهلية الجنس، فلا يُضعف ضمان المخزون) ويرمي
  **403** بجسم منظَّم: `code: 'RIDER_BLOCKED_NO_SHOW'`، رسالة عربية تذكر
  **السبب والتاريخ**، و`blockedUntil` و`noShowCount` و`threshold` و`windowDays`.
  «موقوف» بلا تاريخ تترك الراكب بلا شيء يفعله، وهي بالضبط الحالة التي تولّد
  اتصالاً بالدعم.
- **لا يلغي الحجوزات القائمة.** الحجز المؤكَّد يبقى، ويبقى قابلاً للإلغاء
  والتعديل. إلغاؤه عقوبةً يضرّ السائق أيضاً — يخسر راكباً كان سيأتي — ويحوّل
  عقوبة على سلوك سابق إلى ضرر على رحلة لا علاقة لها.
- **الخادم هو البوّابة.** `GET /bookings/eligibility` موجود ليعرض التطبيق
  الحالة **قبل** أن يملأ الراكب استمارة حجز كاملة ثم يُرفض؛ لكنه إظهار لا
  فرض، وفشله يُعامَل «مسموح» (fail-open) لأن الرفض الحقيقي محفوظ بالخادم.

#### علاقتها بتقييم الراكب — **إشارتان منفصلتان، لا واحدة**

`ratingAvg` **لا يتأثر بعدم الحضور**، والعدّاد يُعرض بجانبه لا داخله. السبب:

- **طبيعتان مختلفتان.** التقييم **حُكم ذاتي** يعطيه طرف واحد عن رحلة **حصلت**؛
  عدم الحضور **واقعة موضوعية قابلة للعدّ** عن رحلة **ما حصلت**. متوسط النجوم
  ما عنده مكان يستوعب «ما جاء أصلاً».
- **الطيّ يُعمي الإشارة.** نجمتان تعني «سائق سيّئ» ونجمتان تعني «راكب تغيّب
  مرتين» ما عاد بينهما فرق يُقرأ. وأسوأ: عدد قليل من الوقائع يسحب المتوسط
  لأسفل بشكل دائم فيصير جزاءً مؤبّداً على سلوك النافذة تعالجه بشهر.
- **الآليتان تتناقضان.** لعدم الحضور **نافذة متدحرجة** و**مسار تظلّم** يُلغي
  واقعة فتخرج من العدّ؛ التقييمات ليس لها لا هذا ولا ذاك — وإضافتهما لها تعني
  إعادة حساب متوسط بأثر رجعي عند كل تظلّم.
- **الجمهور مختلف.** التقييم يُعرض للطرفين علناً؛ العدّاد يراه **السائق فقط**
  على قائمة حجوزات رحلته، وهو مَن يتخذ قراراً عملياً بناءً عليه.

**النبرة: عدد، لا وصف.** ما يظهر للسائق «لم يحضر ٣ مرات مؤخراً» — واقعة
بصيغتها، بلا كلمة «سيّئ» ولا رمز أحمر؛ اللون `warning` لا `danger`، لأن السائق
لا يُطلب منه رفض الراكب بل معرفة السياق. الوقائع الملغاة **لا تُحتسب** بالعدّاد،
فالتظلّم الناجح يختفي من عين السائق كما يختفي من الإيقاف.

#### الفخّ المرتبط (نفس عائلة المشكلة) — من يستطيع الإلغاء ومتى

كان القطع `catchableUntil(trip) − 15min`. مع رحلة «الآن» تُغلق نافذتها والرحلة
تصير `LOCKED` والسائق ما بدأ، فالراكب **لا يقدر يلغي** بينما الرحلة لم تنطلق —
ثم يُؤشَّر عليه `NO_SHOW`. **عقوبة على شيء منعناه من تفاديه.**

**القاعدة الجديدة:** الراكب يلغي (أو يعدّل عدد المقاعد) ما دامت الرحلة `OPEN`
أو `LOCKED`؛ يُرفض عند `EN_ROUTE` فما بعدها.
`booking/booking.service.ts` → `CANCELLABLE_BEFORE`.
الحساب من مصلحة السائق لا من رحمة الراكب: **إلغاء قبل الانطلاق = مقعد يعود
للبيع؛ راكب محبوس = مقعد فارغ *و*واقعة عدم حضور.** الأول أفضل للسائق دائماً.

**وبالمقابل: لا تُسجَّل واقعة إلا على رحلة انطلقت فعلاً.** `POST
/bookings/:id/no-show` مرفوض ما دامت الرحلة `OPEN`/`LOCKED` — السائق لا يقدر
يؤشّر غياباً قبل أن يصل هو نفسه. التأشير والتسجيل يجريان **بمعاملة واحدة**
(`$transaction`) مع إعادة التأكد أن الحجز ما زال `CONFIRMED`: صفّ بلا حالة، أو
حالة بلا صف، كلاهما يفسد العدّ لاحقاً بلا أثر يدلّ عليه.

#### مسار التظلّم (الأدمن) — الشرط الذي يجعل العتبة الحادّة مقبولة

الإيقاف الآلي **حاد عمداً**، وهذا مقبول **فقط** لأن هذا المسار موجود: طارئ
حقيقي (مستشفى، عزاء، عطل) يجب ألّا يساوي حظراً.

- `GET  /admin/no-shows/blocked` → `{ policy, riders[] }` (الموقوفون الآن).
- `GET  /admin/no-shows/rider/:riderId` → السجل كاملاً **بما فيه الملغى**.
- `POST /admin/no-shows/:id/void` `{ reason }` → إلغاء واقعة واحدة.
- `POST /admin/no-shows/rider/:riderId/lift` `{ reason }` → إلغاء كل الوقائع
  المحتسبة داخل النافذة دفعةً واحدة.

**السبب مطلوب** (≥ ٣ أحرف) على الاثنين. الإلغاء **ناعم**: الصف يبقى ومعه السبب
ومَن ألغى — الحذف كان سيمحو الدليل على أن أحداً راجع الحالة أصلاً، والسبب
المكتوب هو **الإشارة الوحيدة** التي ستخبرنا لاحقاً أن العتبة خاطئة.
**رفع الإيقاف يمرّ بالوقائع** لأنها مصدر الحالة؛ رفع بلا إلغاء كان سيعيد
الإيقاف عند أول إعادة تقييم. الوقائع خارج النافذة تبقى: التاريخ لا يُمحى، هو
فقط يخرج من العدّ. وإعادة إلغاء واقعة ملغاة **لا تفعل شيئاً** (`voidedAt: null`
بالشرط) فلا تُبدَّل الأسباب.

اللوحة: **«عدم الحضور»** بالتنقّل الرئيسي — قائمة الموقوفين (تُحدَّث كل ٦٠ ثانية
عبر `RefreshBar`) و`?rider=` تفتح سجل راكب بجانبها.

**قبول:** ٣ وقائع خلال ٣٠ يوماً تمنع الحجز الرابع برسالة تذكر التاريخ، والحجز
القائم يبقى ويبقى قابلاً للإلغاء؛ إلغاء واقعة واحدة يعيد الحجز فوراً؛ رفع
الإيقاف يعمل ويُسجَّل سببه؛ الراكب المحبوس بنافذة «الآن» المغلقة يقدر يلغي؛
والسائق ما يقدر يؤشّر غياباً قبل الانطلاق.

### `safety` (مشاركة الرحلة + جهة اتصال للطوارئ) — Phase 1 amendment

الرحلة ساعة إلى ساعتين بين محافظتين، **مع غرباء**. هذا رهان مختلف تماماً عن
مشوار داخل المدينة، والثقة هي الميزة التنافسية الأساسية هنا (المنافس العراقي
الأبرز تلاحقه شكاوى سلامة). ما كان موجوداً قبل هذا: التقييمات فقط.

> **⚠ كل ما في هذا القسم اختياري ويبدأ من المستخدم.** لا شيء يُشارَك تلقائياً،
> ولا شيء مفعّل افتراضياً، ولا يوجد أي تنبيه أو شارة تدعو لتفعيله. الراكب الذي
> لا يلمس هذه الميزات لا يرى منها شيئاً إطلاقاً — وهذا مُختبَر لا مفترَض
> (`apps/rider/test/safety_test.dart`).

#### ١) «شارك رحلتي»

زر هادئ (`ghost`) على بطاقة «حجوزاتي» وعلى شاشة تأكيد الحجز. يفتح **ورقة معاينة**
فيها نص الرسالة كاملاً، ثم «إرسال عبر واتساب» أو «نسخ النص».

**ليش واتساب لا رسالة داخل التطبيق — القرار المقفول:** لأن **المستلِم ما عنده
التطبيق، ولن يكون عنده**. هي الأم أو الأخ أو الصديقة. أي قناة داخلية تصل فقط
لمن هو مستخدم أصلاً، وهذا يستثني تقريباً كل من يريد الراكب إخباره. وواتساب
موجود بيد كل عائلة عراقية، يشتغل على الواي-فاي وبرصيد صفر، والراكب يختار
المستلِم **من دليل واتساب نفسه** — فالتطبيق لا يخزّن ولا يقترح ولا يرسل لأحد.
الرابط `https://wa.me/?text=…` **بلا رقم** عمداً: ما في مسار كود يقدر يرسل
لشخص لم يخترْه الراكب.

**ليش معاينة قبل الإرسال:** هذه ميزة سلامة، فلازم يشوف الراكب بالضبط ما الذي
يغادر جهازه. تركيب رسالة عن مكانه ومع مَن هو ثم إطلاقها بضغطة واحدة هو عكس
الثقة التي وُجدت الميزة لأجلها. المعاينة **هي** الميزة، لا خطوة تأكيد مضافة.

**محتوى الرسالة** (`packages/shared/lib/share/trip_share.dart` — دالة نقية،
مُختبَرة بالوحدات لأنها المنتج الفعلي للميزة): اسم السائق، السيارة،
**رقم اللوحة**، المسار، وقت الانطلاق، عدد المقاعد. اللوحة هي **الأهم**: هي ما
يميّز هذه السيارة عن كورولا بيضاء أخرى في الكراج.

- **الأرقام:** الوقت وعدد المقاعد **عربية-هندية**؛ **اللوحة تبقى كما هي
  مسجّلة** (غربية) — **معرّف يُطابَق بلوحة معدنية**، من نفس صنف رقم الهاتف
  والإحداثيات، واللوحات العراقية مطبوعة بأرقام غربية.
- **فخّ النقطة، في مكان لا يلتقطه أي golden:** النص يعرضه **واتساب** على جهاز
  لا نملكه بخط لم نختره. فالرسالة لا تضع أبداً فاصلاً نقطياً بجوار رقم
  عربي-هندي، **ولا نقطتين `:` قبل رقم**؛ الحقول تُوصل بكلمات عربية قوية
  («الساعة»، «يوم»، «من … إلى») وكل حقل بسطر مستقل. `٠٧:٣٠` آمن لأن النقطتين
  **بين مقطعَي أرقام** — اتجاه واحد. والمدن تُوصل بـ«إلى» لا بسهم: الخط المرفق
  بلا سهم أصلاً، وخط المستلِم مجهول.
- الحقول الناقصة **تُسقط سطرها** ولا تطبع `null` في رسالة يرسلها راكب لأهله.

**اللوحة تصل مع الحجز فقط.** `/trips/search` **لا** يحملها عمداً — وإلا لجمع
أي شخص لوحات كل السائقين بالتمرير، نفس منطق أرقام الهواتف. تُرجَع من
`POST /bookings` و`GET /bookings/mine` معاً، فالمشاركة تشتغل على شاشة التأكيد
بلا طلب إضافي ينتظره الراكب.

**صفحة حالة عامة (الامتداد الاختياري) — لم تُنفَّذ، وهذا مقصود.** رابط عام
يُعاد توجيهه في واتساب يصير **مقبضاً دائماً بلا مصادقة** على رحلة: كل من في أي
مجموعة أُعيد التوجيه إليها يقدر يتابعها. تقييده يحتاج إصدار رموز وتدويرها
وانتهاء صلاحيتها — ليس رخيصاً. وسطح الويب الوحيد لدينا هو لوحة الأدمن، وجعل
جزء منها عاماً يقلب نموذج تهديدها (كل مساراتها تفترض جلسة أدمن). والعائد ضئيل:
الراكب **داخل السيارة** ويقدر يرسل رسالة ثانية. الرسالة وحدها هي القيمة
الأساسية، وهي منفَّذة.

#### ٢) جهة اتصال للطوارئ

حقلان اختياريان على `User` (`emergencyContactName` + `emergencyContactPhone`)
يضبطهما الراكب من **الإعدادات → الأمان**. فارغة افتراضياً، ولا يُطلب منه أبداً.

- `GET /auth/me` → `emergencyContact: { name, phone } | null`.
- `PATCH /auth/me` `{ emergencyContact }` → كائن **يضبط**، و`null` **يمسح**،
  والغياب **لا يغيّر**. ثلاث حالات مختلفة، ولهذا هو كائن لا حقلان مسطّحان:
  بحقلين ما في طريقة تقول «امسح» تختلف عن «لا تغيّر».
- الاسم **و** الرقم معاً دائماً: رقم مجرّد على شاشة تُفتح تحت ضغط لا ينفع.
  والرقم يُطبَّع بـ`normalizeIraqiPhone` — مصدر الحقيقة نفسه الذي يفحص رقم
  الدخول. ورقم الراكب نفسه مرفوض: الهاتف سيتصل بذاته.

**«اتصال طارئ» يظهر فقط عند اجتماع شرطين:** جهة اتصال **محفوظة**، و**رحلة
`EN_ROUTE`**. وإلا **لا يُرسَم شيء** — لا زر معطّل ولا حالة فارغة ولا دعوة
للتفعيل. وهي حالة (`status`) لا ساعة: `departureTime` لرحلة «الآن» يمضي لحظة
نشرها، فأي اشتقاق من الوقت كان سيضيء الزر على رحلة لم تتحرّك.

**لماذا `danger` الصلب — أعلى صوت بنظام التصميم:** لأنه لا يظهر إلا أثناء رحلة
جارية ولراكب طلبه بنفسه، فهو ليس ضجيجاً دائماً. تحت الضغط، سهولة العثور بضغطة
واحدة تتقدّم على التحفّظ البصري. (الإلغاء غير متاح من `EN_ROUTE` أصلاً، فلا
يتنافس اللونان.) **ولا حوار تأكيد**: `tel:` يفتح **لوحة الاتصال** ولا يُجري
المكالمة — التأكيد خطوة النظام نفسه، وإضافة حوار فوقه تكلّف ثواني في الحالة
الوحيدة التي وُجد الزر لأجلها.

**الحدّ:** هذه بيانات الراكب **عن نفسه**، فما في حدّ كشف بين مستخدمَين — لكن
**ما يجوز أن تغادر صاحبها**. تُرجَع من `GET /auth/me` وحده. المسارات كلها
اليوم `select` صريح فلا تتسرّب، لكن `include: { rider: true }` واحدة مستقبلاً
كانت ستُلحق الصف كاملاً بلا فشل أي اختبار وحدة — فـ`emergency-contact.int-spec.ts`
**يُسلسل الحمولات ويفتّش نصّياً** عن الرقم في قائمة حجوزات السائق، وفي
`/trips/:id/contacts` (المكان الوحيد الذي يخرج منه رقم أصلاً)، وفي `/trips/mine`،
وفي البحث. مُتحقَّق بالحذف: إضافة تسريب متعمّد تُسقط الاختبار.

**إصلاح جانبي وجده هذا العمل:** وصول `trip.status` للتطبيق كشف أن
`canCancel` كان يعرض «إلغاء الحجز» على رحلة `EN_ROUTE` — والخادم يرفضها بـ409.
صار يطابق `CANCELLABLE_BEFORE` تماماً.

**قبول:** الراكب يشارك حجزاً عبر واتساب برسالة تحوي رقم اللوحة (يُتحقَّق من
الرابط ومن النص)؛ «نسخ النص» يشتغل؛ راكب بلا جهة اتصال محفوظة لا يرى أي عنصر
طوارئ في أي مكان؛ ومع جهة محفوظة يظهر الزر أثناء الرحلة فقط ويتصل بالرقم
الصحيح؛ ولا يظهر الرقم لأي مستخدم آخر.

### `admin-support` (أدوات الدعم) — Phase 1 amendment

**المشكلة:** اللوحة كانت تعتمد سائقين وتسعّر ممرات، ولا شيء غير ذلك. أي تدخّل
كان يُنفَّذ بكتابة SQL بـ`psql` — **ثلاث مرات أثناء الاختبار وحده**. ذاك لا
يتوسّع أبعد من شخص واحد، وأول يوم تشغيل حقيقي راح يتصل أحد يقول «حجزي اختفى»
وما في وسيلة لمساعدته.

#### البحث والعرض

- `GET /admin/support/search?q=` → صندوق واحد، ثلاثة أنواع إجابة: رقم هاتف
  (يُطبَّع بـ`normalizeIraqiPhone`، فالراكب يقول «٠٧٧٠…» والأدمن يكتبه كيفما
  اتفق)، أو معرّف رحلة، أو معرّف حجز. الشكل لا يميّز الاثنين (كلاهما cuid)،
  فيُسأل الجدولان بدل إجبار الأدمن على التخمين.
- `GET /admin/support/riders/:userId` → الملف، الحجوزات بحالتها وسياق رحلتها،
  التقييمات المُعطاة والمستلمة، سجل عدم الحضور، وحالة الإيقاف.
- `GET /admin/support/drivers/:profileId` → الملف + المركبة + حالات الوثائق +
  الرحلات + ملخّص الأرباح + التقييمات.
- `GET /admin/support/trips/:tripId` → الرحلة، حجوزاتها بأسماء الركّاب ونقاط
  الصعود/النزول، والسائق الذي أعلنها.

> **«سجل حالة الرحلة» غير موجود، وهذا مذكور بدل أن يُختلق.** ما في جدول تاريخ
> حالات بالـPhase 1. ما يُعرَض هو **ما فعله الأدمن** بهذه الرحلة (من
> `AdminAction`)؛ وما فعلته آلة الحالة وحدها لا يُسجَّل. اختلاق خط زمني من
> الطوابع الزمنية كان سيبدو معلومة وهو تخمين.

#### التدخّل — القاعدة الحاكمة

> **⚠ كل تدخّل يمرّ بنفس خدمة التطبيق التي يستعملها الراكب والسائق.** لا شيء
> هنا يكتب حالةً مباشرة.

| الفعل | يمرّ بـ |
|---|---|
| إلغاء حجز نيابةً عن راكب | `BookingService.cancelAsAdmin` → نفس `cancelBooking` الذي يستعمله الراكب |
| إلغاء رحلة نيابةً عن سائق | `TripService.cancelTripAsAdmin` → نفس `cancelTripRow` |
| إيقاف/رفع إيقاف سائق | `AdminService.suspend` / `unsuspend` |
| إلغاء واقعة / رفع إيقاف راكب | `NoShowService` نفسها (من #46، مُسطَّحة هنا لا مُكرَّرة) |

**ليش هذا حرج:** كتابة الحالة مباشرة كانت ستتجاوز **إعادة المقعد المقفولة
بالصف** و**إعادة فتح الرحلة `LOCKED`→`OPEN`** و**بثّ الإشعارات** — أي ضمان
منع الـoverbooking نفسه، بصمت، وبالضبط على المسار الذي يُستعمل عندما يكون شيء
ما قد اختلّ أصلاً. الفرق الوحيد بين مسار الأدمن ومسار المالك هو **فحص
الملكية**؛ لا شيء غيره.

**ويتبع ذلك أن التدخّل ليس أوسع صلاحية:** إذا كان الراكب لا يقدر يلغي على
رحلة `EN_ROUTE`، فالأدمن كذلك. آلة الحالة قاعدة المنتج، لا مجاملة للراكب.
مُتحقَّق بالحذف: استبدال `cancelAsAdmin` بكتابة حالة مباشرة يُسقط ثلاثة
اختبارات — رجوع المقعد، وإعادة الفتح، ورفض `EN_ROUTE`.

- `POST /admin/support/bookings/:id/cancel` `{ reason }`
- `POST /admin/support/trips/:id/cancel` `{ reason }`
- `POST /admin/support/drivers/:profileId/suspend` · `/unsuspend` `{ reason }`
- `POST /admin/support/no-shows/:recordId/void` · `/riders/:riderId/lift-block`

**«رفع الإيقاف» عن سائق يقبل `SUSPENDED` فقط** — لا `PENDING` ولا `REJECTED`:
الأول لم يُراجَع أصلاً والثاني رُفض لسبب، واعتمادهما بزر «تراجع» كان سيغسل
قراراً لم يتخذه أحد. وهو **ليس** `approve()`: ذاك يبعث «تم اعتماد حسابك» لمن
كان معتمداً ثم أُوقف، فيُقرأ كقرار جديد.

#### سجل الإجراءات

`GET /admin/support/actions?adminId=&entityType=&entityId=` — والصفحة
«سجل الإجراءات» باللوحة. **مَن نفّذ يأتي من الـJWT دائماً**، لا يُرسَل من
العميل: سجل تدقيق يقبل هوية الفاعل من الطلب هو حقل نصّي لا سجل.

**الترتيب: نفّذ ثم سجّل.** الفعل يجري أولاً عبر خدمته، والسطر يُكتب بعد نجاحه.
لو كُتب أولاً لامتلأ السجل بأفعال رفضتها آلة الحالة — وسجل يكذب أسوأ من غيابه.
(الاتجاه المعاكس — نجاح الفعل وفشل الكتابة — ممكن نظرياً، لكنه الاتجاه الصحيح
للخطأ: حالة سليمة وأثر ناقص، بدل حالة سليمة وأثر يصف فعلاً آخر.)

#### الخصوصية

**أرقام الهواتف مرئية للأدمن بحكم الضرورة.** الدعم يبدأ برقم يتصل منه شخص، وما
في وسيلة أخرى لربطه بحسابه. هذا **عرض مميّز** — خلف جلسة أدمن، ولا يظهر لأي
مستخدم آخر — لا عرض عام.

**أما جهة اتصال الطوارئ (#47) فلا تظهر باللوحة إطلاقاً.** هي بيانات الراكب
الخاصة عن نفسه، وما في مهمة دعم واحدة تحتاجها. كل `select` بـ
`admin-support.service.ts` صريح لهذا السبب، و`admin-support.int-spec.ts`
يحرسه بالتفتيش النصّي عن الرقم لا بفحص الحقول — لأن `include: { user: true }`
واحدة مستقبلاً كانت ستُلحق الصف كاملاً بلا فشل أي اختبار وحدة.

**قبول:** الأدمن يجد راكباً برقمه ويرى تاريخ حجوزاته كاملاً؛ إلغاء حجز يعيد
المقعد فعلاً ويُشعر الطرفين؛ كل تدخّل يطلب سبباً ويظهر بالسجل باسم مَن نفّذه؛
الأدمن لا يقدر يلغي على رحلة `EN_ROUTE` كما لا يقدر الراكب؛ ولا تظهر جهة اتصال
طوارئ بأي مكان.

### `route-requests` (طلبات المسارات) — Phase 1 amendment

**المشكلة:** ٣٠٦ ممرات، والسائقون يعلنون على حفنة منها. الراكب الذي يبحث في
مسار بلا عرض يرى حالة فارغة **صحيحة** ثم يغادر — ونحن نبقى نخمّن أي المسارات
تستحق استقطاب سائقين بدل أن يُقال لنا.

- `POST /route-requests` `{ corridorId, requestedFor? }` (راكب مسجَّل).
- `GET  /admin/route-requests?unservedOnly=true` (أدمن) → `{ policy, corridors[] }`.

#### الراكب: نقرة واحدة، بلا نموذج

الزرّ يظهر على **الحالة الفارغة غير المفلترة وحدها**. حالة فارغة بفلتر نشط لها
علاج أرخص («إزالة الفلاتر»)، ولشاشة واحدة فعلٌ رئيسي واحد — والأهم أنها كانت
ستسجّل طلباً على ممرّ لم يسأل البحث المفلتر عن عرضه أصلاً، والعدّ هو كل قيمة
الميزة.

التأكيد **لا يعد بموعد**: «سنخبرك عندما تتوفر رحلات على هذا المسار» بلا «قريباً»
ولا «خلال ...» — ما عندنا موعد، ووعدٌ لا نملكه أسوأ من لا وعد.

#### الازدواج نجاحٌ متكافئ، والقيد في قاعدة البيانات

الفهرس الفريد `(riderId, corridorId, requestedDay)` **هو** قاعدة الـdedupe. حارس
بالتطبيق (اقرأ ثم اكتب) يمرّر نقرتين متزامنتين، وهو بالضبط ما يفعله زرّ يُنقر
مرتين على شبكة عراقية بطيئة — والنتيجة عدّ منتفخ يقرّر استقطاب سائق لمسار لا
يستحقّه. `POST` يرجع ٢٠٠ في الحالتين مع `alreadyRequested`، بنفس منطق «409 من
`POST /ratings` نجاحٌ متكافئ».

«اليوم» يعني **يوم بغداد** لا يوم UTC: نقرة الساعة الواحدة ليلاً يوم كان
سيضمّها مفتاح UTC إلى اليوم السابق، فراكب نقر ١١ مساءً ثم نقر بعد منتصف الليل
كان سيحصل على صفّ واحد ليومين مختلفين عنده.

#### الفان-آوت: اختم ثم اقرأ

عند `POST /trips` وبعد إنشاء الرحلة، يُنادى `RouteRequestService.fulfillForTrip`:

1. **يختم** بـ`updateMany` كل طلب معلّق داخل النافذة على هذا الممر، واضعاً
   `fulfilledAt` و`fulfilledByTripId = trip.id`؛
2. يقرأ الصفوف **بهذا الختم** — معرّف الرحلة جديد في كل نداء، فما يقرأه هو
   بالضبط ما ختمه هو (Prisma لا يرجع صفوف `updateMany`)؛
3. يُشعِر **راكباً واحداً مرة واحدة** (`ROUTE_AVAILABLE`) — قد يملك الراكب
   طلبين معلّقين على نفس الممر (سأل أمس واليوم)، وإشعاران عن رحلة واحدة يقرآن
   كعطل.

الترتيب مقصود: لو قرأنا أولاً ثم أشعرنا ثم ختمنا، لقرأ سائقان يعلنان في نفس
اللحظة نفس الصفوف ولوصل إشعاران. و**لا يرمي أبداً**: الرحلة أُنشئت بالفعل
ومرئية للركّاب، وفشل إشعار لا يجوز أن يُظهر للسائق «تعذّر إعلان الرحلة».

#### الانتهاء: نافذة، لا عمر

`ROUTE_REQUEST_TTL_DAYS` (٣٠، من البيئة، وقيمة فاسدة ترجع للافتراضي). طلب أقدم
منها **لا يولّد إشعاراً ولا يُحتسب في اللوحة**، ويبقى `fulfilledAt = null`:
«محقّق» تعني «أُشعِر صاحبه»، ووسمه كذبٌ في السجل. النافذة **واحدة** يستعملها
الفان-آوت والتجميع معاً — لو اختلفتا لظهر للأدمن طلبٌ لن يُشعَر صاحبه أبداً.

#### اللوحة: الطلب مقابل العرض

الشاشة ترتّب الممرات بالطلب، وتفصل **عدد الطلبات** عن **عدد الركّاب**: خمس
نقرات من شخص واحد مصرّ ليست خمسة أشخاص، والفرق هو ما يمنع قراءة إصرار فرد
كطلبِ سوق. «العرض الحالي» سؤال **حالة** (`OPEN`/`LOCKED`/`EN_ROUTE`) لا ساعة —
رحلة «الآن» وقت مغادرتها يمضي لحظة إعلانها.

`unservedOnly=true` هي القائمة القابلة للتنفيذ: طلب موجود وعرض معدوم. الفلتر
يعيش في العنوان (`?unserved=1`) لا في حالة المكوّن، لأن الشاشة تُحدَّث ذاتياً
كل دقيقة وفلترٌ يضيع كل دقيقة أسوأ من لا فلتر.

**قبول:** راكب على مسار بلا عرض يسجّل رغبته بنقرة، ونقراته المكررة في نفس اليوم
لا تنشئ صفوفاً؛ إعلان رحلة على ممرّ مطلوب يُشعر **بالضبط** مَن طلبه، مرة واحدة،
ويؤشّر طلباتهم محقّقة؛ طلب منتهي الصلاحية لا يولّد شيئاً؛ شاشة اللوحة ترتّب
بالطلب وتعزل الطلب-بلا-عرض.

### `pool` (التجميع) — Phase 2, Stage 1 (خلفية فقط)

**الاتجاه الآخر.** Phase 1: السائق يعلن والراكب يحجز. هنا: الراكب يطلب مقعداً
على ممرّ داخل نافذة وقت، والنظام يجمّع الطلبات المتوافقة، وسائق **يستلم**
التجمّع من لوحة.

**الراكب:**
- `POST   /seat-requests` `{ corridorId, windowStart, windowEnd, pickup, dropoff, seatCount }`
- `GET    /seat-requests/mine`
- `DELETE /seat-requests/:id` (قبل الاستلام فقط)
- `POST   /seat-requests/:id/raise-response` `{ accept }`

**السائق (معتمَد فقط):**
- `GET  /pools/board`
- `POST /pools/:id/claim` `{ departureTime? }`
- `POST /pools/:id/raise` `{ newPricePerSeat }`

#### قاعدة التجميع — لازم تبقى قابلة للشرح لراكب

**نفس الممر + تقاطع النوافذ. لا شيء آخر.** نافذة التجمّع هي **تقاطع** نوافذ
أعضائه: تضيق ولا تتّسع، فأي وقت داخلها يناسب الجميع بالتعريف. لا تحسين مسار
ولا تقليل انحراف في هذه المرحلة — السائق يرى النقاط ويقرّر.

الانضمام **مقارنة-وتبديل**: `updateMany` بحارس يعيد تأكيد النافذة التي قرأناها
ويسقف المقاعد. طلبان يصلان معاً على شبكة بطيئة هما الحالة العادية لا النادرة،
وقراءة-ثم-كتابة كانت ستُدخل الاثنين وتتجاوز السقف. فشل الحارس يفتح تجمّعاً
جديداً — نتيجة صحيحة لا فاسدة.

#### الاستلام: هنا ينتهي Phase 2 ويبدأ Phase 1

الناتج `Trip` بـ`createdBy = SYSTEM` و`SeatBooking` لكل طلب — صفوف لا يميّزها
شيء عن رحلة أعلنها سائق. البدء والإكمال والإلغاء وعدم الحضور والتقييم والأرباح
والإشعارات كلها تعمل بلا سطر جديد. **لا نظام حجز موازٍ.**

السباق (سائقان يضغطان معاً) حارسه `updateMany` مشروط بـ`status = FORMING` —
نفس نمط حجز آخر مقعد. ينجح واحد بالضبط، والخاسر يُخبَر **لماذا**: «استلم سائق
آخر» تعني ابحث عن غيره، و«انخفض العدد» تعني انتظر — نصيحتان متعاكستان.

حساب المقاعد صحيح بالبناء: `seatsAvailable = سعة − مقاعد التجمّع` تُحسب داخل
المعاملة من الطلبات المعلّقة فعلاً. والمقاعد المتبقّية تبقى قابلة للحجز بالمسار
العادي، فتمتلئ السيارة.

#### رفع السعر — المسار الوحيد الذي يتغيّر فيه سعر بعد الالتزام

| الحدّ | كيف يُفرض |
|---|---|
| مرة واحدة لكل تجمّع | `@unique` على `PoolRaise.poolId` — **قيد، لا فحص** |
| مسقوف بـ`Corridor.maxPricePerSeat` | فحص قبل الإنشاء |
| ممنوع داخل `POOL_RAISE_BLACKOUT_MINUTES` من **بداية** النافذة | `canProposeRaise` |
| صاحب الاستلام وحده | `claimedByDriverId` |
| فقط إن بقي مقعد شاغر | `trip.seatsAvailable > 0` |
| مهلة ردّ، **والصمت رفض** | `POOL_RAISE_RESPONSE_MINUTES`، والحسم من المهمّة الدورية |

**الرافض يُطلق بلا أي عقوبة ولا واقعة عدم حضور** — لم يخلف موعداً، بل رفض عقداً
جديداً عُرض عليه بعد أن التزم بغيره. القابل يسافر بالسعر الجديد. وإن قَبِل أقل
من `POOL_MIN_SEATS` مقعداً، **انتهى التجمّع كله**: الرحلة تُلغى ويُطلق الجميع
ويُخبَرون. وبعد الحسم لا يتغيّر السعر أبداً مرة أخرى.

#### الانتهاء

تجمّع مضت نافذته بلا سائق ينتهي، ويُطلق ركّابه **ويُخبَرون** — والإخبار هو
الجزء المهم لا التنظيف. مهمّة دورية بنفس شكل `trip-expiry`، ولا تعتمد عليها
الرؤية: اللوحة والاستلام يفلتران بالنافذة بأنفسهما.

#### حدود مقصودة في هذه المرحلة

- **التجمّعات كلها `GENERAL`.** رحلة نسائية-عائلية تحتاج فرض قاعدة الجنس عند
  **الانضمام** لمجموعة تتكوّن على مراحل؛ مَن يريدها يستعمل رحلات Phase 1
  المعلنة حيث القاعدة مفروضة أصلاً.
- **طلب حيّ واحد لكل راكب على ممرّ بنافذة متقاطعة** — نفس منطق «حجز واحد لكل
  راكب لكل رحلة».
- `POOL_MIN_SEATS = 2` يعني أن تجمّع راكب واحد **لا يصل اللوحة**: ساعة بين
  محافظتين بأجرة مقعد واحد خسارة للسائق. وليس تخلّياً عنه — رحلات السائقين
  المعلنة و«أبلغنا أنك تريد هذا المسار» تخدمانه.

**قبول:** طلبان متقاطعان يتجمّعان وغير المتقاطعين لا؛ الاستلام يُنشئ رحلة
`SYSTEM` بحساب مقاعد صحيح وضمانة Phase 1 قائمة؛ سائقان يستلمان معاً فينجح
واحد؛ رفع فوق السقف أو ثانٍ أو داخل المنع يُرفض؛ الرافض يُطلق بلا واقعة؛
تجمّع بلا سائق ينتهي ويُخبِر ركّابه.

### واجهة الراكب — Phase 2, Stage 2

**Stage 1 خلفية فقط. هذه واجهة الراكب فوقها.** لا واجهة سائق هنا: اللوحة
والاستلام والرفع من جانب السائق هي Stage 3.

المدخل من **البحث**: على النتيجة الفارغة «اطلب مقعد» هو الفعل الأساسي و«أبلغنا
أنك تريد هذا المسار» يُخفَّض إلى فعل هادئ — طلب المقعد قد ينتج رحلة على هذا
الممر فعلاً، بينما تسجيل الرغبة يخبرنا فقط أن نبحث عن سائقين لاحقاً. ويظهر
أيضاً **أسفل النتائج**: ثلاث رحلات بمواعيد لا تناسب هي نفس الطريق المسدود.

النموذج يطلب **نافذة** لا وقتاً واحداً — وهو سبب عمل التجميع أصلاً، ومكتوب على
الشاشة أن توسيع المدة يزيد فرصة الجمع. والسعر **معروض قبل الالتزام** مع
الإجمالي، ومعه الاستثناء الوحيد بصريح العبارة: قد يقترح السائق سعراً أعلى،
والرفض بلا رسوم. وتحته «هذا طلب وليس حجزاً» — **بلا أي وعد بمدّة**، لأننا لا
نملك واحدة.

#### `stage`: القرار على الخادم، والتطبيق يضع البطاقة حيث يُقال له

`GET /seat-requests/mine` يرسل `stage` محسوباً
(`WAITING_FOR_RIDERS` / `WAITING_FOR_DRIVER` / `RAISE_PENDING` / `CLAIMED` /
`CANCELLED` / `DECLINED` / `EXPIRED`). الفرق بين «ننتظر ركّاباً» و«ننتظر سائقاً»
يحتاج `POOL_MIN_SEATS`، وهو رقم سياسة؛ مقارنته بعتبة مكتوبة في Dart كانت ستمنح
السياسة نسختين، وأول تغيير للعتبة يجعل التطبيق يكذب. نفس القاعدة المثبّتة في
«قادمة/سابقة».

و`POST /seat-requests` صار يرجّع **نفس شكل** `/mine` بدل صفّ Prisma خام:
مُحلِّل واحد في التطبيق، لا اثنان يتباعدان عند أول حقل جديد.

#### أين تعيش الطلبات: **فوق الحجوزات في «حجوزاتي»**، لا في تبويب خاص

هذه هي اللحظة التي يلتقي فيها النظامان، والترتيب هو الآلية كلها: حين يستلم سائق
التجمّع، يختفي صفّ الطلب و**تظهر بطاقة حجز عادية مكانها في نفس القائمة** —
بنفس البطاقة وبنفس رقم السائق وبنفس قواعد الإلغاء. تبويب «طلباتي» منفصل كان
سيجعل الحدث نفسه يبدو اختفاءً هنا وظهوراً هناك، وهو بالضبط العالم الموازي الذي
يتجنّبه التصميم.

- الطلبات الحيّة فقط، وتحت «قادمة» فقط — الطلب المنتهي محكيّ في الحجز الذي صاره.
- الحالة الفارغة تحسب الاثنين: راكب كل ما لديه طلب يجب ألّا يُقال له «لا توجد
  حجوزات» فوق بطاقة طلبه.
- الاستطلاع يعمل ما دام **حجز حيّ أو طلب حيّ** موجوداً، والنداءان **متوازيان**
  لا متتاليان: القراءتان تقعان في لحظتين، فإن استلم سائق بينهما ظهر التعارض —
  وبالتسلسل تكون النافذة رحلة كاملة ذهاباً وإياباً، تكفي ليرى الراكب رحلته
  تختفي من القائمتين معاً.

#### شاشة الرفع — بلا أنماط مظلمة

المسار الوحيد في التطبيق الذي يتحرّك فيه سعر بعد الالتزام، فكل خيار فيها في
خدمة أن يبدو **عرضاً** لا فخّاً:

- السعر الحالي والمقترح **جنباً إلى جنب**، ومعهما الفرق والإجمالي الجديد
  محسوبَين — لا حساب ذهني تحت ضغط الوقت.
- **السعر الحالي لا يُشطب.** الشطب يقول «هذا لم يعد سارياً»، والراكب لم يقرّر
  بعد؛ وهو الرقم الذي يجب أن **يقرأه** ليحكم. جُرّب الشطب وأظهرت اللقطة أنه صار
  أصعب الرقمين قراءة — وهو عكس المطلوب.
- **لا خيار مُسبق الاختيار**، والرفض بنفس العرض والارتفاع مباشرة تحت القبول —
  لا رابط نصّي ولا تحت الطيّة.
- **المهلة وقت صريح لا عدّاد تنازلي**: العدّاد يصنع إلحاحاً لا تقتضيه الحالة.
  ومكتوب أن الصمت رفض، ليعرف مَن وضع هاتفه أن ذلك آمن.
- **«الرفض مجاني تماماً: لا رسوم، ولا يُحتسب غياباً»** — مكتوبة بالكلمات، لأن
  هذا بالضبط هو الخوف الذي وُجدت الشاشة لتجيب عنه.

**قبول:** «اطلب مقعد» يُوصل من البحث (فارغاً وبنتائج)؛ النموذج يطلب نافذة
ويعرض السعر قبل الإرسال ولا يعد بمدّة؛ الطلبات تظهر في «حجوزاتي» بحالاتها
ويمكن إلغاء غير المستلَم؛ الاستلام يستبدل الطلب ببطاقة حجز كاملة (رقم السائق،
تعديل المقاعد، الإلغاء)؛ شاشة الرفع تعرض السعرين والفرق والمهلة وتنصّ على
مجانية الرفض، ولا شيء فيها مُسبق الاختيار.

### واجهة السائق — Phase 2, Stage 3

**تغلق الحلقة.** قبلها كان الراكب يطلب ويتكوّن التجمّع ويصل اللوحة — ولا أحد
يستطيع استلامه إلا بنداء API مباشر.

**المدخل: «العمل».** التبويب الأول صار سطحاً واحداً بمقطعَين — «انشر رحلة»
و«التجمّعات» — لا تبويباً سادساً: `FloatingPillNav` يؤكّد حداً أقصاه خمسة وقد
اكتملت، وهذا القيد فرض السؤال فجاء الجواب أفضل من البديل. نشر رحلة واستلام
تجمّع جوابان لسؤال **واحد** («كيف أملأ صباحي؟»)، فمكانهما سطح واحد يقارن بينهما
لا مكانان يتذكّر السائق أن يتفقّدهما. وعدّاد اللوحة يظهر على الشريط نفسه، ولهذا
تُحمَّل اللوحة **مرة عند فتح التطبيق** لا عند فتح التبويب: عدّادٌ لا يظهر إلا
بعد أن تجد الشيء الذي يدلّ عليه بلا فائدة.

**البطاقة تجيب سؤالاً واحداً — «هل تستحق القيادة؟»** بأربع كتل: أين ومتى
(**النافذة**، لا وقتاً واحداً)، وكم امتلأت مقابل سعة السيارة، وكم تدفع **الآن
ولو امتلأت**، وهل النقاط عملية. يُحذف سطر «لو امتلأت السيارة» حين يملأ التجمّع
السيارة أصلاً: طباعة الرقم مرتين تطلب من السائق مقارنة عدد بنفسه.

**تباعد نقاط الصعود بخط مستقيم — وهذا ليس تحسين مسار.** لا ترتيب ولا طريق
مقترح؛ يجيب فقط «هل النقاط متقاربة أم عبر المدينة؟»، وهو ما لا يُعرف إلا بفتح
كل نقطة على خريطة. والحدود خشنة عمداً: قرار نعم/لا، لا قياس.

#### رفض الاستلام يحمل **رمزاً**، والتطبيق يفرّع على الرمز

| الرمز | ماذا يعني للسائق |
|---|---|
| `POOL_ALREADY_CLAIMED` | سبقك غيرك — **ابحث عن تجمّع آخر** |
| `POOL_EXPIRED` / `POOL_WINDOW_PASSED` | لم يعد قائماً — لا أحد أخذه |
| `POOL_NOT_VIABLE` | ألغى راكب — **انتظر**، قد يعود |
| `POOL_EXCEEDS_CAPACITY` | أكبر من سيارتك — لم يكن لك أصلاً |

نفس شكل الـ409 المبنيّ المستعمل في `RIDER_BLOCKED_NO_SHOW`. مطابقة النص العربي
بدلاً منه كانت ستنكسر بصمت عند أول تحسين صياغة — والفحص السابق للاستلام كان
يجيب «لم يعد متاحاً» عن **حقيقتين مختلفتين** (استلمه غيرك، وانتهت مهلته).

#### رفع السعر — تحذير قبل الالتزام لا رفضاً بعده

`GET /pools/mine/:tripId` يرجّع السعر والسقف والمهلة و`canPropose` **محسوباً من
نفس شروط** `proposeRaise`، ومعه `blockedReason` بالعربية حين يكون الجواب «لا».
زرٌّ يعرضه التطبيق ثم يرفضه الخادم أسوأ من غياب الزر — نفس القاعدة المثبّتة في
`ratable` و`stage`. و`null` جواب صحيح لا خطأ: رحلة أعلنها السائق لا تجمّع لها.

الشاشة تعرض **ثلاث نتائج لا واحدة**: الآن، ولو وافق الجميع، و**لو وافق الحد
الأدنى فقط** — لأن الرافض يُطلق، فسعرٌ أعلى للمقعد قد يعني مالاً أقلّ وركّاباً
أقلّ. الحساب في `raise_projection.dart`، نقيّ ومختبَر بالوحدة، لأن القرار كله
يقوم عليه. وعند `POOL_MIN_SEATS` بالضبط تتغيّر نبرة النص: السائق لا يخاطر بأجرة
أصغر بل بالرحلة كلها. ويفتح المُعدِّل على **درجة واحدة فوق السعر الحالي، لا على
السقف**، فلا تُقرأ الشاشة كتوصية بأخذ الحد الأعلى.

بعد الإرسال: **حالة انتظار مقروءة** — مَن وافق ومَن رفض ومَن لم يردّ، بالأسماء
وبالمقاعد، والمهلة كوقت صريح. والمُطلَق يبقى **على القائمة** موسوماً: «أين ذهب
الثالث؟» سؤال يطرحه السائق، وحذف الصف يجعل الجواب اختفاءً.

#### الحلقة كاملة — اختبار واحد يمشيها من طرفها إلى طرفها

`services/api/src/pool/phase2-loop.int-spec.ts`: يطلب راكبان ← يتكوّن التجمّع ←
يصل اللوحة ← يستلمه سائق ← **يحجز راكب ثالث المقعد الأخير بالمسار العادي** ←
تنطلق ← صعود وعدم حضور ← تكتمل ← الأرباح تساوي بالضبط أجرة مَن ركب ← التقييم في
الاتجاهين. كل ما بعد الاستلام يُستدعى من **خدمات Phase 1** التي لم ترَ تجمّعاً
قط؛ لو افترضت إحداها `createdBy = DRIVER` لسقطت هنا وحدها.

**قبول:** يتصفّح السائق اللوحة ويستلم فتظهر في «رحلاتي» كرحلة عادية؛ استلامان
متزامنان ينجح أحدهما والخاسر يقرأ «استلمه سائق آخر» تحديداً؛ الرفع لا يتجاوز
السقف ولا يتكرّر ولا يقع داخل المنع، ولكلٍّ رسالته؛ السائق يرى ردود الركّاب
والمهلة؛ والتجمّع المستلَم يكمل دورته حتى الأرباح والتقييم.

### `notification`
- `POST /devices` `{ token }` (FCM). أحداث تُطلق إشعار: حجز جديد (للسائق)، تأكيد حجز (للراكب)، تذكير مغادرة، إلغاء رحلة، بدء/إكمال.
**قبول:** الأحداث الرئيسية تُطلق إشعارات فعلاً.

#### مركز الإشعارات داخل التطبيق — Phase 1 amendment

الـ push موجود لكن **معطّل**: ينتظر بيانات اعتماد Firebase، فحالياً يسجّل بالـ
log فقط. هذا القسم هو النصف الذي **يشتغل اليوم**، ويكمّل الـ push لاحقاً بدل أن
يستبدله.

- `GET  /notifications` → `{ unreadCount, notifications[] }` (الأحدث أولاً، بحد
  أقصى ٥٠ صفاً) — طلب واحد يغذّي القائمة والشارة معاً.
- `GET  /notifications/unread-count` → `{ unreadCount }`.
- `POST /notifications/:id/read` — idempotent؛ `404` لصف غير موجود، `403` لصف
  يخصّ مستخدماً آخر.
- `POST /notifications/read-all`.

> **ترتيب المسارات:** `read-all` مُعرَّف **قبل** `:id/read` بالـ controller،
> وإلا التقط `:id` الكلمة `read-all` كمعرّف.

**باعث واحد، مصرفان.** كل حدث يمرّ بـ `NotificationService.send(userId, payload)`
التي **تخزّن الصف ثم تحاول الـ push**. ممنوع أن يبعث أي module إشعاراً بطريق
آخر — الـ fan-out (مَن يستلم ماذا) مُثبَّت باختبارات تكامل حقيقية في
`notification-fanout.int-spec.ts`، لأن `findMany` المُقلَّد لا يطبّق `where`
أصلاً فلا يثبت شيئاً.

**مَن يستلم ماذا:**

| الحدث | الراكب | السائق |
|---|---|---|
| حجز جديد | `BOOKING_CONFIRMED` | `BOOKING_CREATED` |
| الراكب ألغى حجزه | `BOOKING_CANCELLED` | `BOOKING_CANCELLED_BY_RIDER` |
| السائق بدأ الرحلة | `TRIP_STARTED` | — |
| السائق أنهى الرحلة | `TRIP_COMPLETED` (+ دعوة تقييم) | — |
| **السائق ألغى الرحلة** | `TRIP_CANCELLED` لكل راكب حجزه غير ملغى | — |
| اعتماد/رفض السائق | — | `DRIVER_APPROVED` / `DRIVER_REJECTED` |
| **سائق أعلن على ممرّ مطلوب** | `ROUTE_AVAILABLE` لكل راكب طلبه (مرة واحدة) | — |

`TRIP_CANCELLED` هو **الحدث الوحيد الحاجب** بالتطبيق: يوقف الواجهة بحوار لا
يُغلق بالضغط خارجه ولا بزر الرجوع، وله زر إقرار واحد. السبب مباشر — مَن يفوته
هذا الخبر يذهب ليقف عند نقطة انطلاق لسيارة لن تأتي. كل ما عداه توست عابر.

### `earnings` (نقدي)
- `GET /driver/earnings?range=` (يومي/إجمالي). يُسجَّل عند إكمال الرحلة.
**قبول:** أرباح اليوم تظهر صح للسائق بعد رحلة مكتملة.

## 5. الشاشات
**تطبيق الراكب:** (1) onboarding: هاتف→OTP→اسم · (2) بحث: ممر + تاريخ/وقت + from/to · (3) نتائج (كروت: وقت، سعر/مقعد، مقاعد متبقية، تقييم السائق) · (4) تفاصيل + حجز: أشّر نقطة الصعود والنزول على الخريطة + عدد المقاعد → تأكيد (cash) · (5) حجوزاتي (قادمة/سابقة) · (6) متابعة الرحلة (معلومات السائق + الحالة) · (7) تقييم السائق · (8) الملف.
**تطبيق السائق:** (1) onboarding + رفع مستمسكات (هوية، إجازة سوق، تسجيل مركبة) → بانتظار الاعتماد · (2) إعلان مسار (ممر، الآن/مجدول، مقاعد) · (3) رحلاتي + حجوزات كل رحلة (راكب، صعود/نزول، مقاعد) · (4) إدارة الرحلة: بدء/إكمال/إلغاء، onboard/no-show · (5) الأرباح · (6) تقييم الركّاب · (7) الملف.
**لوحة الأدمن:** (1) دخول باسم مستخدم + كلمة مرور · (2) Dashboard (عدّادات) · (3) اعتماد السواق + مراجعة المستمسكات · (4) مراقبة الرحلات · (5) الممرات والتسعير · (6) إدارة المدراء (**للمدير الأعلى فقط**) · (7) بحث/دعم أساسي.
> اللوحة Next.js بنفس نظام تصميم "مَسار" (صنوبري/زعفراني على ورق دافئ) وعربية RTL، والأرقام المعروضة عربية-هندية والإدخال غربي — نفس قاعدة التطبيقين.
> تصميم الشاشات تفصيلياً: يُطبَّق سكل `ui-ux-pro-max` بمرحلة الـ UI.

## 6. قواعد تجارية مهمة
- **مخزون المقاعد:** transactional حصراً (قسم booking).
- **التسعير (Phase 1 amendment — يحدده السائق):** **السائق** يحدد سعر المقعد عند نشر الرحلة؛ الممر يعطي **اقتراحاً** (`suggestedPricePerSeat`) وحدّين (`min`/`max`) يضبطهما الأدمن. الأجرة تبقى `fare = trip.pricePerSeat × seatCount` بلا تغيير.
  - **لماذا:** هيك تشتغل الكراجات العراقية فعلياً (السائق يعلن سعره)؛ السعر الواحد الثابت ما ينفع لمسارات تختلف مسافاتها اختلافاً كبيراً؛ ويصير بإمكان الراكب يقارن أسعار السائقين على نفس المسار.
  - **الحدود** تحمي من الخطأ المطبعي ومن الاستغلال، بلا ما تلغي حرية السائق. الترحيل اشتق حدوداً واسعة عمداً (٥٠٪ – ٢٠٠٪ من السعر القديم، مقرّبة لأقرب ٢٥٠ IQD) حتى لا يتحوّل ترحيل بيانات إلى قرار منتج صامت؛ الأدمن يضيّقها لكل ممر من اللوحة.
- **قفل الرحلة:** تلقائي عند `seatsAvailable=0` أو عند `departureTime`؛ أو يدوي ببدء السائق.
- **No-show (Phase 1 amendment — نُفّذت):** السائق يعلّمها **على رحلة انطلقت
  فقط** (`EN_ROUTE` فما بعد) → تُسجَّل واقعة بنفس المعاملة →
  **٣ وقائع خلال ٣٠ يوماً = إيقاف حجز ٧ أيام** (كلها متغيّرات بيئة).
  **لا خصم مالي** — الدفع نقدي فما في ما يُخصم منه. الحجوزات القائمة لا تُلغى،
  والأدمن يقدر يلغي واقعة أو يرفع الإيقاف بسبب مسجَّل. التفاصيل بقسم `no-show`.
- **إلغاء الراكب (Phase 1 amendment):** مسموح ما دامت الرحلة `OPEN`/`LOCKED`،
  ومرفوض بعد `EN_ROUTE` — بدل قطع «١٥ دقيقة قبل المغادرة» الذي كان يحبس ركّاب
  رحلات «الآن» بلا مخرج. تعديل عدد المقاعد يتبع نفس القاعدة.
- **إلغاء السائق للرحلة:** كل الحجوزات CANCELLED + إشعار الركّاب فوراً.
- **الهوية:** رقم الموبايل هو المفتاح؛ مستخدم واحد بدورين ممكن.
- **الجنس مطلوب (Phase 1 amendment):** `gender` يُضبط بالتسجيل؛ الملف مكتمل عند الاسم+الجنس. لا يقدر راكب بلا جنس أن يحجز أي رحلة (`403` — أكمل الملف).
- **رحلة نسائية/عائلية (`WOMEN_FAMILY`) — Phase 1 amendment:** **كل الركّاب يجب أن يكنّ إناثاً** (المرأة تحجز مقاعد إضافية للعائلة)، بينما **السائق قد يكون ذكراً أو أنثى** — يطابق واقع العرض العراقي. تُفرض الأهلية على الخادم عند `POST /bookings` **قبل** معاملة حجز المقعد (فلا تُضعف ضمان الـ transactional). الراكب قد يفلتر اختيارياً بجنس السائق (`driverGender`)، وقائمة فارغة نتيجة صالحة.

## 7. ترتيب البناء لـ Claude Code (كل خطوة قابلة للاختبار)
1. **Scaffold + DB + `auth`** → *milestone:* دخول بواتساب OTP يشتغل.
2. **`driver` + اعتماد الأدمن** → *milestone:* سائق يُعتمد.
3. **`corridor` + `trip` posting** → *milestone:* سائق يعلن رحلة نجف↔كربلاء.
4. **`booking` (بحث + حجز transactional)** → *milestone:* راكب يحجز، المخزون صحيح، لا overbooking.
5. **`trip-lifecycle` + `earnings`** → *milestone:* رحلة كاملة تكتمل، النقد مسجّل.
6. **`rating` + `notification`** → *milestone:* تقييم + إشعارات رئيسية تشتغل.
7. **Admin dashboard + صقل** → *milestone:* معايير قبول Phase 1 تتحقق.
> اختبر رحلة كاملة (حجز→ركوب→نقد→تقييم) قبل ما تنتقل للـ milestone التالي.

## 8. معايير قبول Phase 1 (تعريف "خلصت")
- سائق يسجّل، يُعتمد، يعلن رحلة نجف↔كربلاء بمقاعد وسعر.
- راكب يبحث، يلگّيها، يحجز مقعد مع صعود/نزول؛ المقاعد تنخصم صح بلا overbooking.
- السائق يبدأ ويكمل الرحلة؛ النقد يُسجَّل أرباح؛ الطرفان يتقيّمون.
- الإلغاء والـ no-show مُعالَجان؛ الإشعارات تشتغل.
- كله عربي RTL، IQD، Asia/Baghdad، WhatsApp OTP، Android.
